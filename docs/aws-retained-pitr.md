## Documented mechanism and eligibility limits

RDS supports retained automated backups for PostgreSQL DB instances. They contain system snapshots and transaction logs and do not consume the DB-instance quota. They expire according to the original retention policy; deleting an instance does **not** establish a new guaranteed 24-hour recovery window. Parameter and option groups are not retained. [AWS retained-backup documentation](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.Retaining.html).

For this same-region, deleted-source case, `RestoreDBInstanceToPointInTime` accepts **`SourceDbiResourceId`**. The source-identifier selector requires an existing instance; the automated-backup ARN selector is documented for replicated backups. The controller pins the physical source ID and an explicit earlier `RestoreTime`; it never substitutes latest-time or snapshot restore. [Restore API](https://docs.aws.amazon.com/AmazonRDS/latest/APIReference/API_RestoreDBInstanceToPointInTime.html).

Deletion must explicitly set **`DeleteAutomatedBackups=false`**; its default is destructive to backups. Deletion protection must first be removed. Once instance deletion begins, it cannot be cancelled. The proposed synthetic experiment sets `SkipFinalSnapshot=true`: this deliberately sacrifices the disposable source and adds no manual snapshot. This is a bounded portfolio experiment, not production backup guidance. [Delete API](https://docs.aws.amazon.com/AmazonRDS/latest/APIReference/API_DeleteDBInstance.html).

The first run established Ohio access, two permitted micro instances and one-day retention; the later run observed retained-backup restore availability on that account. This is a dated execution result, not a guarantee of current or general Free-plan eligibility. There is no restore `DryRun` API, and IAM analysis cannot establish Free-plan/SCP eligibility. **Full native recovery acceptance remains incomplete.** If a future authorized retention or restore request is rejected, preserve the real error, perform approved cleanup and report failure; never upgrade the account. [RDS getting started](https://docs.aws.amazon.com/AmazonRDS/latest/gettingstartedguide/create-instance-overview.html) · [Free-plan conditions](https://docs.aws.amazon.com/hands-on/latest/control-your-costs-free-tier-budgets/control-your-costs-free-tier-budgets.html).

## Executable sequence and destructive-transition gates

The manifest selects `retained-two-instance-v1`, maximum instances `2`, source scope `disposable_synthetic_control_only`, and `receipt-ledger-sha256-v1`. Execution additionally requires the approved manifest hash, `--execute`, `--approve-retained-source-deletion`, and a fresh `--private-checkpoints` directory inside ignored `.local/`.

1. Deploy only after separate approval. Independently verify the new guard, deployment clock and checker. Provision exactly control and independent receipt instances: private, encrypted, Single-AZ PostgreSQL 17.11, `db.t4g.micro`, 20 GB gp3 each, one-day retention, no storage autoscaling.
2. Bootstrap separate SQL identities, require empty ledgers, capture a database-clock baseline and observe an active automated-backup window covering it **before** committing the synthetic intent. Commit the independent receipt, replay exactly, and reconcile original `1/1` state with effective read-only mutation denials.
3. Drain all one-off tasks and freeze controller writes. Require the exact regional instance set; refuse replicas, foreign instances, changed physical IDs, disabled keys or less than 90 minutes remaining before cleanup. This drains this isolated controller's actors; it is not proof against unrelated administrator writes.
4. Require an available encrypted automated source snapshot at or before the baseline, plus conservative retention headroom beyond the cleanup deadline. Require the active backup's physical identity, region, engine, size, key, one-day retention and `EarliestTime <= baseline < LatestTime`, intersected with the live instance's latest-restorable bound. Logs can lag; a timestamp guessed from elapsed time is insufficient. [AWS PITR behavior](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html).
5. Tag the exact automated-backup ARN, independently read its ownership tag, persist source/remote IDs in the conditional inventory registry, and save a private checkpoint locally and in encrypted guard storage with exact byte read-back. Automated-backup tags are independent of DB tags; inheritance is never assumed. [AWS tagging behavior](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_Tagging.html).
6. Recheck identity/window/tag/drain/guard, remove protection on **control only**, then delete it with retained backups. Wait for typed instance-not-found and a regional inventory containing **only receipts**. Require the actual backup to be `retained`, with the same ARN and a still-valid window. Read its tag again and save a second verified checkpoint. No source deletion is attempted without the preconditions; no restore is attempted merely because deletion was accepted.
7. Restore using the original physical ID and baseline. Reapply the captured subnet, security groups and parameter group; force private Single-AZ micro configuration and protection. Check inherited retention, adjusting only the restored target to one day through `ModifyDBInstance` if needed. The pinned SDK does not accept retention as a restore input. Require a distinct restored physical ID and the original enabled key. Peak sequence is **control + receipts → receipts → restored control + receipts**.
8. Execute two read-only reconciliations against restored control and the unchanged independent receipt database. Each must show `0` intents, `1` effect, exactly `remote_ahead_missing_intent`, `safe_to_resume=false`, two effective SQL mutation denials, and an unchanged canonical receipt-content SHA-256. Retain the same remote physical ID throughout. Because original control was deleted, its pre-deletion `1/1` checkpoint replaces the old experiment's post-restore original comparison; do not claim that original still exists.

The receipt fingerprint includes ordered keys, hashes, bodies and receipt IDs under a repeatable-read, read-only transaction; counts alone cannot establish unchanged content. The fixture is still `synthetic_SQL_intent_not_worker_dispatch`. This lane does not prove HTTP dispatch, production services, application restart, Multi-AZ recovery or a production deployment.

If deletion acknowledgement is lost, the controller stops with its durable checkpoint; it does not blindly retry the entire fixture, move the baseline, reapply Terraform to recreate control, or claim success. Operator inspection and the independent cleanup guard own this failure path. Restore rejection after source deletion can leave only the receipt instance and retained backup until cleanup. That risk requires explicit approval.

Independent checkpoints need exact guard-bucket read/write and guard-key encryption/decryption. Existing ECS execution and SQL identity separation remain. No Oracle-only password option, tenant permission, new cross-account role or Paid-plan authority is introduced. Conditional dependent IAM actions must be evaluated against the actual request, not blindly copied from a generated action list. [RDS authorization reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_rds.html).

The watchdog retains its separate role; backup deletion remains `rds:DeleteDBInstanceAutomatedBackup` on Ohio `auto-backup:*` **conditioned on this exact run's resource tag**. Both reader roles can inspect backup tags. Cleanup refuses an unverified backup and retains the key while any database, snapshot or backup remains. The read-only checker cannot create, restore, delete or tag resources. Static IAM analysis is supporting review, not proof of effective permissions or SCP acceptance.
