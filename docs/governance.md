# Identity, authority and agent control

## Identity contract

The canonical ID is a UUID generated by the control layer. `(source, subject)` is a durable mapping, never a caller-supplied canonical override on a source event. Only a new CRM subject with a supplied email and no existing email candidates can create a customer. Existing mappings resolve deterministically. All other unmapped records become review exceptions.

Email is case-folded for this synthetic identity convention. No provider-specific plus/dot rewriting, phone matching, name similarity, enrichment or fuzzy merging occurs. Even one exact email candidate requires review: shared/recycled addresses exist. More than one candidate is explicitly ambiguous. A later authoritative CRM email update may make two existing customer emails equal; this does not merge their IDs.

An operator links a source subject with a target revision and written evidence. Rebinding an existing subject is forbidden. Each customer has at most one authoritative subject per source so independent record sequence clocks are not accidentally compared. Record replacement, customer merges/splits and source migrations require a future reviewed migration workflow. The operator's asserted evidence is audited, not independently verified by an external identity provider.

An unresolved original event remains unresolved in the immutable ledger after linking. Repeating its ID returns the original decision. Request a new delivery identity after review; its field sequence may remain the original value if no observation was accepted. This makes reprocessing explicit without rewriting history.

## Field ownership

| Field | Authoritative source | Rule |
|---|---|---|
| email, phone, owner | CRM | Closed formats; newer accepted sequence for that field |
| lifecycle | CRM | Lead < MQL < SQL < Opportunity < Customer; cannot move backward |
| score | scoring | Strict integer 0–100; may increase or decrease |
| consent | consent | Strict boolean; no consent means no marketing permission |
| suppressed | privacy | Strict boolean; unknown or true blocks marketing |

The source sequence is a monotone version within that source record, not a wall clock. Provenance stores source, subject, event ID and accepted sequence per field. An older observation can fill a field that has never had a newer accepted observation, but cannot overwrite that field's newer value. Rejected observations are retained in event/audit history and do not become authoritative field watermarks. A source event can therefore have both accepted and denied fields; the complete decision map and any governance exception are committed atomically.

Repeated event identity plus identical normalized content returns the original result. The same identity with changed normalized content produces an idempotency exception and cannot change state. Unrecognized keys, empty updates, explicit null values and coercions such as string booleans are rejected. Deleting a field requires a separate future policy, not an ambiguous null patch.

Every newer accepted observation increments the customer revision, even if its value is unchanged. This conservatively invalidates previously reviewed context. It can create extra approvals but prevents silent reuse of stale context.

## Proposal and permission contracts

`Proposal` requires a UUID request ID, canonical customer, exact revision, action, bounded rationale and an allow-listed template. There is no arbitrary target URL, executable tool name, free-form mutation dictionary, email recipient override or source override. The deterministic simulator exercises the same API as any agent. No LLM is needed to prove this boundary.

| Action | Policy | Effect |
|---|---|---|
| `sync_profile` | Autonomous when context is current | Internal synthetic profile snapshot; not marketing contact |
| `send_marketing` | Current consent, known clear suppression, email and human approval | Synthetic marketing effect for the canonical email and named template |
| `set_consent` | Always denied to agent | No work row; reviewable denial |

Approvals are bound to the proposal hash, customer revision, policy hash and expiry. Proposal TTL is 15 minutes; approval TTL is at most five minutes and never extends the proposal. Duplicate approvals do not refresh expiry. Self-approval is forbidden, and the agent credential cannot reach the approval endpoint. Current policy and state are checked again when claiming permission to dispatch. An operator requeue never edits the payload, key, approval or revision.

Authentication uses distinct configured local bearer tokens with startup validation. Tokens stand in for identities in the reproducible example; OIDC, scoped service accounts, tenant isolation, request rate limiting and centralized credential rotation are production reference requirements. This single-tenant API allows the agent to read any synthetic customer by ID. Do not present it as a production authorization system for sensitive customer data.
