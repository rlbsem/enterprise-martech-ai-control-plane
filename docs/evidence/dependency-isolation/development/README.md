## Follow-up liveness correction

Later source review identified a real defect behind the short-profile sensitivity: every successful request set a 50-millisecond pacing delay. A fast receipt GET returning 404 could therefore repeatedly defer its immediately following POST. Passing the earlier 300-second runs did not rule out this starvation path. The current runtime removes pacing after successful requests; shared failure cooldown, per-destination budgets and concurrency bounds remain. A focused PostgreSQL counterexample executes the preserved old implementation, and a structural regression checks that successful receipt lookup leaves dispatch eligible. The first counterexample assertion expected exactly 50 milliseconds and failed on a measured 49.999 milliseconds from separate database clock calls; the assertion now checks the positive unintended delay rather than an unstable microsecond boundary. Both original observations and source remain preserved.

Corrected-runtime qualification and software verification are recorded separately in the [current acceptance entry point](../portability-fix/README.md). The original four run directories, manifests, software verification and timeline are historical and retain their original bytes. An explicit two-file source map resolves the original source hashes; it does not substitute outcomes or relabel old executions as corrected-runtime proof.
